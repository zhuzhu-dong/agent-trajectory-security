# Agent 轨迹记录与轨迹安全

这个仓库做了一个最小但**真实**的 Agent 实验，分两步：

1. **记录**：用 LangGraph + 真实模型 API + 三个本地工具搭一个 Agent，把它执行过程中的每一步（模型调用、工具调用、观测结果）完整记录下来。
2. **攻击这些记录**：拿第一步**真实产生**的轨迹做安全分析——它会泄露什么？多层检测能不能找出来？脱敏之后这份记录还有没有用？围绕它的访问控制是不是真的会拒绝？

关键点是：第二步的输入不是手写的样本，是第一步真实跑出来的产物。

所有凭据都是合成的。**真实的模型 API 密钥从不写入任何产物**，只记录它的 sha256 指纹——因为"为了演示凭据会泄露、而把一把活凭据写进一个专门用来泄露的数据集"是错的取舍。

## 环境与运行

Python 3.12，依赖见 `requirements.txt`（langgraph 1.2.0 / langchain 1.3.1 / langchain-openai 1.2.1）。除 pydantic 外，实验二全部用标准库——bootstrap 和 Wilson 区间都是闭式解，不需要 scipy。

```bash
cp .env.example .env          # 填入 DEEPSEEK_API_KEY
python run_experiment.py --all   # 跑完两个实验并生成报告
python -m pytest agentlab/tests trajsec/tests -q   # 37 个断言
```

`--e1 --mock` 用脚本化替身跑通全流程、不调 API，适合改代码时用。**报告里的数字只来自真实运行。**

## 实验一：真实 Agent 轨迹记录

手写 LangGraph 图（`agent ↔ tools` 循环，显式节点边界），模型走 DeepSeek 的 OpenAI 兼容端点，工具是沙箱内的 `read_file` / `run_shell` / `sql_query`。

**两种插桩来源，缺一不可：**

- **框架层**（LangChain callback）：拿到 token 用量、精确耗时、发给模型的完整 prompt、被框架吞掉的异常。
- **运行时层**（图 stream）：拿到节点跃迁、每次路由选了哪条边。

callback 看不到图走了哪条边，stream 拿不到 token 用量。记录器按 run id 和节点名把两者合并成一条有序轨迹。

**轨迹格式里有六项是被实验二的需求倒逼出来的**，事后补代价极大：偏移量一律指向 JSON Pointer 下的**解码后字符串**（否则检测和脱敏对偏移的理解会不一致，回放测试静默失效）；每步带 `provenance.untrusted` 污点标记；截断可见；脱敏会破坏哈希链因此要记 `original_chain_hash`；OTel 风格的 span id；以及顶层的 `sandbox_declaration` 声明哪些密钥是真的。

### 结果（44 条真实轨迹）

| 指标 | 值 |
|---|---|
| 运行数 / 场景数 | 44 / 11 |
| 步骤 / 模型调用 / 工具调用 | 554 / 144 / 222 |
| 工具错误 | 26（沙箱拒绝 + 模型试错，全部如实入库） |
| token / 成本 | 242,538 / **$0.038** |
| **模型耗时占比 : 工具耗时** | **97.4% : 2.6%** |
| 哈希链校验 | 44/44 通过 |

那个 97.4 : 2.6 本身是个结论：**Agent 的墙钟时间几乎全花在模型上，工具执行可以忽略。**

### "可复用"的三条硬证据

存了个 JSON 证明不了复用。三条独立证据，且都能**离线从产物复核**（`python run_experiment.py --stats-only`）：

1. **重建一致 44/44** —— 仅从轨迹重建整个对话，与实跑的消息列表做摘要比对。更强的一点：这个校验用的是回调记录的 `messages_in`（模型实际收到的 prompt）作为独立视图，两者必须互相印证。
2. **回放一致 36/36** —— 不调模型、不碰文件系统，把记录下来的模型输出和工具观测喂回去，重建出等价执行。
3. **断点续跑** —— 在工具调用前中断，恢复后继续，工具调用正确链回原请求 span。

## 实验二：轨迹安全

### 威胁模型（明确边界）

在范围内：静态泄露、交第三方、跨租户越权读取（IDOR）、**提示注入把密钥带进轨迹**、内部人过度读取、记录篡改、过度脱敏摧毁审计价值。

明确排除：网络与 OS 层攻击、内存抓取、侧信道、真实 KMS 隔离、多机分布式信任、恶意管理员。本地单机测不了的，不假装解决。

### 四层检测器

- **L1 格式** —— 锚定正则 + **结构校验**（JWT 要能 base64 解码出带 `alg` 的 JSON；DSN 要 `urlsplit` 出密码；PEM 要 BEGIN/END 配对）。只匹配形状是不够的。
- **L2 上下文** —— 最值钱的一层。键名规则（`AUTH_TOKEN=` 里的值即使没有任何格式特征也命中）、路径策略、dotenv/shell dump 子解析器、**嵌套结构**（连接串里单独标出密码分量，让脱敏能只替换最小 span）、有界再编码展开、污点加权。
- **L3 熵** —— **按字符集类别归一化**。原始 Shannon 熵不可跨形状比较：20 字符 hex 上限约 4 bits，base64 约 6，而一句长英文能到 4.2——任何固定原始阈值都会同时漏掉 hex 密钥、狂报英文散文。
- **L4 策略** —— 白名单压制 + 已知值黑名单。它必须压住轨迹自己的哈希链字段：64 位 hex，熵上与密钥不可区分，而它不是密钥。

### 结果（5 个种子 × 360 注入项，输入是 44 条真实轨迹）

| 指标 | 值 |
|---|---|
| item recall（标出位置） | **0.925 ± 0.060** |
| item recall（还原出值） | 0.800 ± 0.060 |
| precision | **0.933 ± 0.007** |
| 自然轨迹误报 | 2612 条 finding / 53 误报 = **2.0%** [1.6%, 2.6%] |
| 红队 | **22/22**，无未配对拒绝 |

两个 recall 回答的是不同问题：*标出位置*是"检测器有没有指出密钥在哪"，*还原出值*是"有没有真的拿到那个值"。规避手段会把两者分开——base64 包裹的密钥能被就地标出，却永远还原不出明文。混成一个数字就把最该知道的事藏起来了。

**跨种子稳定性**：0.925 这个数字比单种子最好情况低，全部方差都来自 T4 层（见下）。

### 分层消融：这是整个实验最诚实的地方

| 配置 | span recall | precision | Δrecall | Δprecision |
|---|---|---|---|---|
| 仅 L1 | 0.625 | 1.000 | — | — |
| +L2 | 0.875 | 0.941 | +0.092 | −0.059 |
| +L3 | 1.000 | 0.572 | +0.008 | **−0.370** |
| +L4 | 1.000 | 0.932 | 0.000 | **+0.360** |

**熵层只买到 +0.8 点召回，却付出 37 点精确率，全靠白名单层事后收回 36 点。** 说它是成功的层是假的；说它没用也错——它是唯一能碰到"无前缀、非敏感键名"那类密钥的层。

### 头条结论：检测失败即授权失败

因为记录的密级由检测器输出**推导**，一个漏检的密钥 = 一条被低估分级的记录 = 明文进入交给第三方的产物。

| 配置 | 记录数 | P(被低估分级) | P(明文进入导出) |
|---|---|---|---|
| 满栈 | 180 | 0.60 | 0.60 |
| **去掉 L3** | 180 | **1.00** | **1.00** |

不是断言，是**拿掉一层看它出现**。

### 访问控制与审计

- **推导式分级**：`record.classification = max(基础密级, 各 finding 类型密级的格上 join)`。
- **默认拒绝，未知动作 fail-closed**。
- **职责分离是刻意的**：管理员管策略但读不到内容；审计员读审计但读不到内容；属主读内容但管不了策略。没有单一角色能既伪造又掩盖。
- **每条拒绝都配对一条正向对照**——一个全部拒绝的测试套件，在存储无差别拒绝一切时也会通过。22 条用例，无未配对拒绝。
- **审计日志哈希链 + Merkle root + 外部锚**。篡改检出率诚实报 **5/6**：`FORGE_APPEND`（看起来合法的追加）**检不出**，因为链本身不可能检出它。诚实的声称是"可检出能写记录但不能写锚的主体所做的篡改"——`FORGE_APPEND` 恰恰是反例，所以把它放进了测试并如实报告。

### 脱敏：结构保持，最小 span

- **格式保持 token** —— 等长同字符集替换。换成 64 位 hex 摘要会破坏下游解析器，也会破坏偏移稳定性。
- **最小 span** —— `postgresql://appuser:<token>@host:5432/prod`：host、user、port、库名都有用且不秘密，摧毁它们是可测的可用性损失。
- **低熵值不按值 token 化** —— HMAC 是 PRF 不是慢 KDF，且单机上攻击者手里就有密钥。对一个 6 字符密码做相关性是设计错误，所以低熵值改用带类型计数器占位符，**主动放弃相关性**。
- **token 作用域是策略旋钮** —— 全局稳定的 token 本身就是泄露：能读两个租户轨迹的人可以确认同一凭据出现在两边。默认 run 作用域，跨 run 不可关联、run 内保留。
- **可用性损失量化** —— 路径保持率 1.000、审计答案一致率 1.000、再扫描幂等、破坏足迹 0.089（只重写了 8.9% 的字节）。

**认证的边界说清楚**：单机上两个档位是**策略隔离，不是密码学保证**。持密钥者可逆；单向档之所以单向，只是因为从不写 vault。DPAPI 防的是机器上的其他用户，不防同一用户或管理员。

## 需要如实说明的几点

**预注册的 H1 被证伪。** 事先定的假设是"L3 对 T4 层的召回提升 ≥ 15 点、精确率代价 ≤ 5 点"。实测 +0.125、代价 +0.37。报告如实写 refuted，**没有回头改阈值**。

**熵层跨种子不稳定。** 校准选出的阈值 0.81 恰好压在被检测总体的熵上（40 字符随机字母数字的归一化熵约 0.79–0.82），所以 T4 检出跨种子从 0.875 到 1.000 波动，**基本是抛硬币**。阈值在测试集打分前冻结，之后没有调过。这是实测出来的弱点，不是调掉的。

**跨字段拆分和零宽字符插入检不出。** 明文不在任何单个 span 里，值级检测器原理上做不到。在预注册里就声明为预期失效，从 headline 里排除、单独列行，而不是事后找借口。

**自然文本误报的判定是保守的。** 只有值精确等于已植入的已知凭据才算真阳性，所以真实但非凭据形状的泄露（内网主机名、路径）被算成了误报——报出的 2.0% 是**上界**。

**白名单可被控制字段名的攻击者绕过。** 一个把密钥藏在名为 `hash` 或 `build_id` 的字段里的攻击者会被漏掉。L4 是误报控制，不是对抗性过滤器。

**样本量决定一切区间。** bootstrap 按**轨迹**聚类重采样（同一条 run 内的 finding 是相关的），所以每个置信区间的宽度由独立运行条数决定，而不是密钥条数。更多轨迹是这份工作最便宜的可信度改进。

## 开发过程中被评测驱动的四处修改

都记在 `PREREGISTRATION.md` 的偏离章节里，因为它们虽然发生在测试集打分**之前**，但每一处都是看到评测输出才发现的：

1. **语料把两条轴混在了一起** —— 规避模式按 tier 随机抽取，导致某一层全部落到预期失效档，那层存在的意义（测难度）样本数为零。熵层因此看起来毫无贡献。已改成两条正交轴。
2. **L4 的十六进制压制太宽** —— 48 字符窗口内出现任意白名单词就压制，把一个真实的 32 位 hex `AUTH_TOKEN` 误杀了。改为要求密钥由白名单名**紧邻引导**。
3. **`looks_like_word` 误杀了约一半随机字母数字密钥** —— 元音比例检验作用在原始 token 上。改为先要求 token 几乎全是字母。
4. **重建校验比对错了对象** —— 它拿存储的产物和**另一次全新运行**做对比。真实模型是非确定性的，两次的消息列表本来就不同。改为在产生该轨迹的那次运行内校验。
